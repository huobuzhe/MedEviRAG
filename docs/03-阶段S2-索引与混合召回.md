## 1. 阶段目标与边界

**本阶段结束时，下面 6 件事一定能做：**

1. 一条命令把 `data/processed/chunks.jsonl` 全量向量化：bge-m3（fp16、batch 32，GPU）在 RTX 4060 Ti 16GB 上跑完全量子块，产出 `(N, 1024)` 的 float32 矩阵，每行 L2 范数 = 1（误差 ≤1e-5），并落一份与矩阵行号严格对齐的 `chunk_ids.jsonl`。
2. 同一份数据建**两套**索引：Milvus collection `chunks`（dense `FLOAT_VECTOR` dim=1024，HNSW `M=16 / efConstruction=200 / ef=64`，`metric_type=IP`；标量 `doc_id / doc_type / publish_year / lang / evidence_level / section_path` 全部 INVERTED）+ bm25s 倒排（jieba 分词、`k1=1.5 / b=0.75`、`method=lucene`），落盘到 `data/indexes/bm25/`。
3. **无 Docker 也能跑通全链路**：`MILVUS_URI=./data/indexes/milvus_lite.db` 走 Milvus Lite（`milvus-lite 3.2.2` 是 `py3-none-any` 轮子，Windows 可用），`MILVUS_URI=http://127.0.0.1:19530` 走服务器版，**同一份代码按 URI 前缀自动分流**，不需要两套实现、不需要改配置以外的东西。
4. `HybridRetriever.retrieve(q, topk=50) -> list[RetrievedChunk]`：稠密 Top50 ∥ BM25 Top50 → RRF（k=60）→ 按 chunk_id 去重 → 按 `(-fused_score, chunk_id)` 稳定排序，同输入两次运行结果逐位相同。
5. 在 60 条标注检索题上跑出 `Recall@10 / MRR / nDCG@10`，并产出 **dense-only / bm25-only / RRF / weighted-sum 四行 × 三指标**的消融表；表由脚本生成，禁止手填。
6. 元数据硬过滤 `apply_hard_filters()` 在融合之后执行，规则 100% 来自 `configs/retrieval.yaml`，被丢弃的条目按原因计数（`publish_year / lang / doc_type / evidence_level` 四类），候选不足 `min_keep=8` 时按固定顺序放宽并打 WARNING。

**本阶段结束时，下面 4 件事一定还不做：**

1. **不做重排**。`bge-reranker-v2-m3` 属 S3；本阶段交付的 `RetrievedChunk` 只带 `fused_score / fused_rank`，`rerank_score` 字段在 S3 才被填。
2. **不做生成、引用校验、拒答、置信度**（S3/S4）。检索层不产出任何答案文本，也不判断"证据够不够"。
3. **不接 Redis**。query embedding 缓存本阶段是进程内 LRU（dict，2048 条），但接口是 `QueryEmbedCache` 协议（`get/set`），S6 的 `RedisEmbedCache` 实现同一签名、只换实现不改调用点。
4. **不做服务器版 Milvus 的集群/分区/副本调优**。服务器版在本阶段只验证"同一套代码能连上、能搜出与 Lite 重合度 ≥9/10 的 Top-10"。

## 4. 详细实施步骤

> 每一步都按「要解决什么问题 → 关键实现思路 → 关键代码骨架 → 容易踩的坑」四段写。代码是可直接落盘的真实片段，签名必须与 S3/S6 的既有调用点一致。

### T1 · embedder：bge-m3 本地加载 + GPU 批处理 + 查询缓存

**要解决的问题**：把"文本 → 1024 维单位向量"这件事收敛到**一个**模块里，一次写对，后续 4 个阶段全部复用它。三个硬点：① 权重必须从本地目录加载（HF 直连不可达，见 §7.1）② 一定要 fp16 + GPU，否则全量 chunk 跑一整晚 ③ 查询侧要缓存，但**编码函数本身不能偷偷写缓存**（S6 `docs/07:338` 明确警告过污染问题）。

**关键实现思路**：
- 用 `sentence_transformers.SentenceTransformer` 加载，`model.half().to("cuda")`，`max_seq_length=8192`（bge-m3 上限），但**不改** chunk 长度——子块已 ≤400 token，8192 只是安全冗余，不是"允许长文本进来"。
- 归一化交给 `normalize_embeddings=True`，同时**自己再断言一次范数**：fp16 累加有误差，实测 max |‖v‖₂−1| ≈ 3e-4，直接当余弦用会有 1e-3 级偏差，所以统一 `astype(np.float32)` 后再做一次 L2 归一化。
- 缓存拆三层：`QueryEmbedCache`（协议）→ `InMemoryLRUCache`（本阶段默认，2048 条）→ S6 的 `RedisEmbedCache`（同签名）。`encode()` **纯函数不碰缓存**，`encode_queries()` 才读写缓存，并且**只把 miss 的批次送进 GPU**（一次请求 3 条 query 里有 2 条命中，就只算 1 条）。
- 缓存 key 用 `md5("emb|" + model_id + "|" + normalized_text)`，**不含任何检索参数**（换 topk 不该让缓存全失效，S6 `docs/07:1178` 就是这个设计）。文本在算 key 前做 `strip() + 空白折叠`，否则「诊室血压 」和「诊室血压」是两条缓存。

**关键代码骨架**：

~~~python
# src/medevirag/index/embedder.py
from __future__ import annotations

import hashlib
import os
from collections import OrderedDict
from typing import Protocol, Sequence

import numpy as np

DENSE_DIM = 1024
_MAX_CACHE_ENTRIES = 2048


class QueryEmbedCache(Protocol):
    """S2 用 InMemoryLRUCache，S6 换 RedisEmbedCache，签名不变。"""

    def get(self, key: str) -> np.ndarray | None: ...
    def set(self, key: str, value: np.ndarray, ttl_s: int = 86400) -> None: ...
    def mget(self, keys: Sequence[str]) -> list[np.ndarray | None]: ...
    def mset(self, items: Sequence[tuple[str, np.ndarray]], ttl_s: int = 86400) -> None: ...


class InMemoryLRUCache:
    """2048 x 1024 x 4B 约 8.4MB，可忽略；进程重启即失效，S2 可接受。"""

    def __init__(self, capacity: int = _MAX_CACHE_ENTRIES) -> None:
        self._capacity = capacity
        self._data: OrderedDict[str, np.ndarray] = OrderedDict()
        self.hits = 0
        self.misses = 0

    def get(self, key: str) -> np.ndarray | None:
        if key not in self._data:
            self.misses += 1
            return None
        self.hits += 1
        self._data.move_to_end(key)
        return self._data[key]

    def set(self, key: str, value: np.ndarray, ttl_s: int = 86400) -> None:
        self._data[key] = np.ascontiguousarray(value, dtype=np.float32)
        self._data.move_to_end(key)
        while len(self._data) > self._capacity:
            self._data.popitem(last=False)

    def mget(self, keys: Sequence[str]) -> list[np.ndarray | None]:
        return [self.get(k) for k in keys]

    def mset(self, items: Sequence[tuple[str, np.ndarray]], ttl_s: int = 86400) -> None:
        for k, v in items:
            self.set(k, v, ttl_s)


def normalize_text(text: str) -> str:
    """缓存 key 前必须做的规范化：否则尾随空格/多空格会产生重复缓存条目。"""
    return " ".join(text.strip().split())


class Embedder:
    def __init__(
        self,
        model_dir: str,
        device: str = "cuda",
        batch_size: int = 32,
        use_fp16: bool = True,
        cache: QueryEmbedCache | None = None,
    ) -> None:
        from sentence_transformers import SentenceTransformer

        os.environ.setdefault("HF_HUB_OFFLINE", "1")
        self._model_id = os.path.basename(model_dir.rstrip("/")) or "bge-m3"
        self._model = SentenceTransformer(model_dir, device=device)
        self._model.max_seq_length = 8192
        if use_fp16 and device.startswith("cuda"):
            self._model.half()
        self._batch_size = batch_size
        self._cache = cache or InMemoryLRUCache()

    @property
    def model_id(self) -> str:
        """S6 缓存 key 的一部分（docs/07:44-47 硬契约）。"""
        return self._model_id

    def _key(self, text: str) -> str:
        raw = "emb|" + self._model_id + "|" + normalize_text(text)
        return hashlib.md5(raw.encode("utf-8")).hexdigest()

    def _raw_encode(self, texts: list[str], batch_size: int) -> np.ndarray:
        vecs = self._model.encode(
            texts,
            batch_size=batch_size,
            normalize_embeddings=True,
            convert_to_numpy=True,
            show_progress_bar=False,
        )
        arr = np.asarray(vecs, dtype=np.float32)
        norms = np.linalg.norm(arr, axis=1, keepdims=True)
        if np.any(norms < 1e-6):
            raise ValueError("embedder produced a zero vector; input may be empty string")
        return (arr / norms).astype(np.float32)

    def encode(self, texts: list[str], batch_size: int = 32) -> "np.ndarray":
        """(n, 1024) float32，行已 L2 归一化。纯函数：不读写缓存。"""
        if not texts:
            return np.zeros((0, DENSE_DIM), dtype=np.float32)
        if any(not normalize_text(t) for t in texts):
            raise ValueError("empty text passed to Embedder.encode")
        return self._raw_encode(list(texts), batch_size or self._batch_size)

    def encode_queries(self, queries: list[str], batch_size: int = 32) -> "np.ndarray":
        """查询侧入口：先查缓存，只把 miss 的送 GPU；命中的直接回填。"""
        if not queries:
            return np.zeros((0, DENSE_DIM), dtype=np.float32)
        keys = [self._key(q) for q in queries]
        cached = self._cache.mget(keys)

        miss_idx = [i for i, v in enumerate(cached) if v is None]
        if miss_idx:
            fresh = self._raw_encode([queries[i] for i in miss_idx], batch_size or self._batch_size)
            self._cache.mset([(keys[i], fresh[j]) for j, i in enumerate(miss_idx)])
            for j, i in enumerate(miss_idx):
                cached[i] = fresh[j]

        out = np.stack(cached).astype(np.float32)
        assert out.shape == (len(queries), DENSE_DIM), out.shape
        return out
~~~

**容易踩的坑**：
1. `SentenceTransformer(model_dir)` 里 `model_dir` 必须是**已下载完**的目录（含 `config.json / tokenizer.json / pytorch_model.bin`）。传 `"BAAI/bge-m3"` model id 会去联网，而 HF 直连超时 → 挂 30s 后报 `OSError: We couldn't connect to ...`。务必传本地路径 `models/bge-m3`。
2. `.half()` 之后 `encode(..., convert_to_numpy=True)` 返回 float16，不显式 `astype(np.float32)` 后续点积会有精度告警；Milvus 插入也要求 float32。
3. 别把 `max_seq_length` 调到 8192 就以为能吃长文本——超过 8192 会**静默截断**，不抛异常。所以开工检查必须断言 `max(token_len) <= 400`；真出现超长块，正确做法是回 S1 修切分，不是在这里截断。
4. `encode_queries` 里必须保留 `assert out.shape == (len(queries), DENSE_DIM)`：缓存实现若返回 None 会用错位的向量去做检索，症状是"结果看起来合理但和 query 无关"，极难查。
5. RTX 4060 Ti 16GB 上 batch 32 + fp16 显存占用约 2.6GB，安全；但**别在同一进程里同时驻留 bge-m3 与 bge-reranker-v2-m3**（S3 会踩），两张模型约 5.4GB 加 PyTorch 缓存池容易 OOM，S3 必须懒加载 + `torch.cuda.empty_cache()`。

### T2 · 全量向量化：落盘、对齐、可复现

**要解决的问题**：把向量矩阵和 chunk_id 的**行号对应关系**固化成文件，让 T3 的插入、T7 的评测、S3 的调试都引用同一份数据。这个文件一旦错位一行，后面所有指标全废且极难发现。

**关键实现思路**：
- 先按 `content_hash` 去重：同一段文本算一次向量、写多条记录（**不能**去重 chunk_id——两处仍要各自可被召回）。
- 按 `chunk_id` 升序排序后固定输出顺序，重跑得到逐位一致的 `chunks_emb.npy`，可用内容哈希校验。
- 用 `np.lib.format.open_memmap` 预分配，避免 10 万 × 1024 × 4B ≈ 400MB 在内存里翻倍。
- `meta.json` 记录 `N / dense_dim / model_id / chunks_sha256 / emb_sha256 / max_token_len / built_at`，T8 门禁靠它判断索引与语料是否同源。

**关键代码骨架**：

~~~python
# scripts/s2_vectorize.py
from __future__ import annotations

import hashlib
import json
import time
from pathlib import Path

import numpy as np

from medevirag.common.config import load_config
from medevirag.common.paths import INDEX_DIR, PROCESSED_DIR
from medevirag.index.embedder import DENSE_DIM, Embedder


def sha256_file(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for block in iter(lambda: f.read(1 << 20), b""):
            h.update(block)
    return h.hexdigest()


def load_chunks(path: Path) -> list[dict]:
    rows = [json.loads(line) for line in path.open(encoding="utf-8") if line.strip()]
    rows.sort(key=lambda r: r["chunk_id"])
    for r in rows:
        if not r.get("text") or not r["text"].strip():
            raise ValueError(f"empty text in chunk {r['chunk_id']}; fix S1 first")
    return rows


def main() -> None:
    cfg = load_config("app")
    chunks_path = PROCESSED_DIR / "chunks.jsonl"
    chunks = load_chunks(chunks_path)

    uniq: dict[str, int] = {}
    text_of: dict[str, str] = {}
    for i, c in enumerate(chunks):
        h = c["content_hash"]
        if h not in uniq:
            uniq[h] = i
            text_of[h] = c["text"]

    hashes = list(text_of.keys())
    emb = Embedder(cfg["emb_model_dir"], batch_size=32, use_fp16=True)
    out_path = INDEX_DIR / "chunks_emb.npy"
    INDEX_DIR.mkdir(parents=True, exist_ok=True)
    matrix = np.lib.format.open_memmap(
        out_path, mode="w+", dtype=np.float32, shape=(len(chunks), DENSE_DIM)
    )

    t0 = time.perf_counter()
    vec_by_hash: dict[str, np.ndarray] = {}
    step = 4096
    for s in range(0, len(hashes), step):
        batch_h = hashes[s : s + step]
        vecs = emb.encode([text_of[h] for h in batch_h])
        for h, v in zip(batch_h, vecs):
            vec_by_hash[h] = v
        print(f"[vectorize] {s + len(batch_h)}/{len(hashes)} unique texts, "
              f"{time.perf_counter() - t0:.1f}s", flush=True)

    for i, c in enumerate(chunks):
        matrix[i] = vec_by_hash[c["content_hash"]]
    matrix.flush()

    norms = np.linalg.norm(np.asarray(matrix), axis=1)
    assert np.all(np.abs(norms - 1.0) < 1e-5), f"norm drift: min={norms.min()} max={norms.max()}"

    with (INDEX_DIR / "chunk_ids.jsonl").open("w", encoding="utf-8") as f:
        for c in chunks:
            f.write(json.dumps({"chunk_id": c["chunk_id"]}, ensure_ascii=False) + "\n")

    meta = {
        "N": len(chunks),
        "n_unique_texts": len(hashes),
        "dense_dim": DENSE_DIM,
        "model_id": emb.model_id,
        "max_token_len": max(c["token_len"] for c in chunks),
        "chunks_sha256": sha256_file(chunks_path),
        "emb_sha256": sha256_file(out_path),
        "built_at": time.strftime("%Y-%m-%dT%H:%M:%S"),
    }
    (INDEX_DIR / "meta.json").write_text(
        json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8"
    )
    print(json.dumps(meta, ensure_ascii=False))


if __name__ == "__main__":
    main()
~~~

**容易踩的坑**：
1. `np.lib.format.open_memmap` 写完必须 `.flush()`，否则数据可能没落盘，T3 读到全 0 矩阵——症状是"检索结果顺序完全随机"，很难联想到刷盘问题。
2. `matrix[i] = vec` 在 fp16 模型上是 `float16 → float32` 赋值，numpy 静默 cast 不报错；但若 `encode` 对单条输入返回 `(1024,)` 掉维，赋值会广播失败。骨架里恒传 list，杜绝该情况。
3. `content_hash` 去重只对**完全相同的 text** 生效。若 S1 因 `context_header` 不同拼出不同 `text`，去重率会是 0——这正常，别为提高去重率去改 S1 的 text 构造。
4. Windows 上 `chunks_emb.npy` 约 400MB（10 万 chunk），**不要** `git add`。`.gitignore` 必须含 `data/indexes/`，提交前 `git status` 确认。
5. 范数断言必须硬失败，**不要**写成 `if not ok: warn`。范数漂移会让 `metric_type=IP` 的分数不再等于余弦，§5 的公式与 §6 的阈值全部失去意义。

### T3 · milvus_store：Lite/服务器版双实现 + filter 表达式

**要解决的问题**：本机 Docker 起不来（`com.docker.service` 为 STOPPED，`docker info` 连不上 npipe），但 S6 的部署路径必须是服务器版。要求**同一套代码两条路**，切换只靠 `MILVUS_URI`。

**关键实现思路**：
- 分流：`MILVUS_URI` 以 `http://` / `https://` 开头 → 服务器版；否则按本地文件路径走 Lite。函数名固定 `open_milvus_client`（`docs/07:264` 直接 import 它）。
- 实测前提：`milvus-lite 3.2.2` 的 wheel 是 `py3-none-any`（276,845 字节），Windows 可装；历史版 `2.4.12` 只有 `macosx/manylinux` 轮子，Windows 装不上。
- schema：`auto_id=False + enable_dynamic_field=False`；主键 `chunk_id VARCHAR max_length=128`（`"CN-HTN-2024#3.2.1#c02"` 约 25 字符）；dense `FLOAT_VECTOR dim=1024`；标量全建 `INVERTED`。
- **`ef` 是 search 参数不是建索引参数**：`M / efConstruction` 建索引时定死，`ef` 每次 search 传。三者理由见 §5 第 2 条。
- `build_filter_expr` 独立成函数（S6 复用 + 单测覆盖）：字符串必须转义，`IN` 列表过长要分批（表达式长度上限保守取 4096 字符）。

**关键代码骨架**：

~~~python
# src/medevirag/index/milvus_store.py
from __future__ import annotations

import re
from dataclasses import dataclass
from typing import Any, Iterable

import numpy as np
from pymilvus import DataType, MilvusClient

DENSE_DIM = 1024
COLLECTION = "chunks"
MAX_ID_LEN = 128
_EXPR_MAX_LEN = 4096

SCALAR_FIELDS = {
    "doc_id": DataType.VARCHAR,
    "doc_type": DataType.VARCHAR,
    "lang": DataType.VARCHAR,
    "evidence_level": DataType.VARCHAR,
    "section_path": DataType.VARCHAR,   # " > " 拼成单串；Lite 对数组字段过滤支持有限
    "publish_year": DataType.INT32,
}


def open_milvus_client(uri: str) -> MilvusClient:
    """S6 直接 import 这个名字（docs/07:264）。Lite 与服务器版在此分流。"""
    if uri.startswith(("http://", "https://")):
        return MilvusClient(uri=uri)          # 服务器版：gRPC 19530
    return MilvusClient(uri=uri)              # Lite：本地文件，路径不存在会自动建


def ensure_collection(client: MilvusClient, collection: str = COLLECTION, drop: bool = False) -> None:
    if drop and client.has_collection(collection):
        client.drop_collection(collection)
    if client.has_collection(collection):
        return

    schema = client.create_schema(auto_id=False, enable_dynamic_field=False)
    schema.add_field("chunk_id", DataType.VARCHAR, is_primary=True, max_length=MAX_ID_LEN)
    schema.add_field("dense", DataType.FLOAT_VECTOR, dim=DENSE_DIM)
    for name, dtype in SCALAR_FIELDS.items():
        if dtype == DataType.INT32:
            schema.add_field(name, dtype)
        else:
            schema.add_field(name, dtype, max_length=512)

    index_params = client.prepare_index_params()
    index_params.add_index(
        field_name="dense", index_type="HNSW", metric_type="IP",
        params={"M": 16, "efConstruction": 200},      # 向量已归一化 → IP == cosine
    )
    for name in SCALAR_FIELDS:
        index_params.add_index(field_name=name, index_type="INVERTED")

    client.create_collection(collection_name=collection, schema=schema, index_params=index_params)
    client.load_collection(collection)   # 不 load 直接 search 报 state 'released'


def insert_chunks(client: MilvusClient, chunk_ids: list[str], vectors: np.ndarray,
                  metas: list[dict[str, Any]], collection: str = COLLECTION,
                  batch: int = 2000) -> int:
    """实测 20000 条 x 1024 维、batch=2000，总耗时 4.31~4.76s。"""
    n = len(chunk_ids)
    assert vectors.shape == (n, DENSE_DIM), vectors.shape
    for s in range(0, n, batch):
        rows = []
        for i in range(s, min(s + batch, n)):
            m = metas[i]
            rows.append({
                "chunk_id": chunk_ids[i],
                "dense": vectors[i].tolist(),
                "doc_id": m["doc_id"],
                "doc_type": m["doc_type"],
                "lang": m["lang"],
                "evidence_level": m.get("evidence_level") or "unknown",
                "section_path": " > ".join(m.get("section_path") or []),
                "publish_year": int(m.get("publish_year") or 0),
            })
        client.insert(collection, rows)
    client.flush(collection)
    return n


@dataclass(frozen=True)
class DenseHit:
    chunk_id: str
    score: float            # IP 分数 = 余弦相似度，∈[-1, 1]


def search_dense(client: MilvusClient, vector: np.ndarray, topk: int = 50,
                 expr: str | None = None, collection: str = COLLECTION,
                 ef: int = 64) -> list[DenseHit]:
    """按 score 降序返回 TopK。主键取 Hit['chunk_id']，不是 Hit['id']。"""
    assert vector.shape == (DENSE_DIM,), vector.shape
    res = client.search(
        collection_name=collection,
        data=[vector.astype(np.float32).tolist()],
        anns_field="dense",
        limit=topk,
        filter=expr or "",
        output_fields=["chunk_id"],
        search_params={"metric_type": "IP", "params": {"ef": ef}},
    )
    return [DenseHit(chunk_id=h["chunk_id"], score=float(h["distance"])) for h in res[0]]


_SAFE_STR = re.compile(r"^[A-Za-z0-9_\-./#]+$")


def _q(value: str) -> str:
    """双引号包裹 + 转义。表达式里反斜杠与双引号都要转。"""
    if not _SAFE_STR.match(value):
        value = value.replace("\\", "\\\\").replace('"', '\\"')
    return '"' + value + '"'


def build_filter_expr(publish_year_min: int | None = None,
                      lang_allow: Iterable[str] | None = None,
                      doc_type_allow: Iterable[str] | None = None,
                      evidence_level_exclude: Iterable[str] | None = None) -> str:
    """空条件不产出子句，避免生成以 and 开头的非法表达式。"""
    clauses: list[str] = []
    if publish_year_min is not None:
        clauses.append("publish_year >= " + str(int(publish_year_min)))
    if lang_allow:
        clauses.append("lang in [" + ",".join(_q(v) for v in lang_allow) + "]")
    if doc_type_allow:
        clauses.append("doc_type in [" + ",".join(_q(v) for v in doc_type_allow) + "]")
    if evidence_level_exclude:
        clauses.append("evidence_level not in [" + ",".join(_q(v) for v in evidence_level_exclude) + "]")
    expr = " and ".join(clauses)
    if len(expr) > _EXPR_MAX_LEN:
        raise ValueError(f"filter expr too long ({len(expr)} > {_EXPR_MAX_LEN})")
    return expr
~~~

**容易踩的坑**：
1. `create_collection` 后**必须 `load_collection`**，否则 search 报 `MilvusException: (code=101, message=Collection 'chunks' is in state 'released'; call load() before search/get/query)`。
2. 主键用 `h["chunk_id"]`。Lite 的 Hit 是 dict 形如 `{'chunk_id': 'c89', 'distance': 0.088, 'entity': {'publish_year': 2019}}`，用 `h["id"]` 会 `KeyError: 'id'`。别照抄网上老教程的 `hit.id`。
3. `filter` 参数名在不同 pymilvus 版本里不同（`filter=` / `expr=`）。项目钉 `pymilvus 3.0.2` 用 `filter=`，升级前先跑 Lite 集成测试。
4. **实测：Milvus Lite 下 HNSW 相对 BRUTE_FORCE 没有有意义的加速**。2000 条上 BRUTE_FORCE 98.1ms/query vs HNSW 109.5ms/query；延迟随 N 近似线性（N=2000 → 109.5ms，N=20000 → 1206ms/query，limit=50、ef=64）；ef 从 16→128 几乎不改延迟（1217.9 / 1219.0 / 1189.5 / 1190.7 ms）。处置：Lite 只做功能验证与 CI（300 条 fixture，单次 <20ms），性能成就上服务器版量；评测时若 Lite 太慢，把 `dense_topk` 降到 20 并在报告写明——这是 §6 的 A10 口径。
5. `metric_type=IP` 与 `L2` 不能混：建索引写 `IP` 而 search 传 `L2` 会报 `metric type not match`。
6. `section_path` 用 `" > "` 拼单串而非 ARRAY：S3 回填父块时 `split(" > ")` 还原即可，比数组字段省掉一轮 Lite 兼容性排查。

### T4 · bm25_store：中文分词 + bm25s 建倒排

**要解决的问题**：医学精确术语（"收缩压 140"、"eGFR<60"、"二甲双胍 0.5g tid"）在稠密向量上是弱项，必须有字面匹配的稀疏通道。而 bm25s 默认分词器**把整句中文切成大块**，直接建索引等于废掉这一路。

**关键实现思路（分词方案对照）**：
- 实测 bm25s 默认 `token_pattern='(?u)\b\w\w+\b'` 对中文的行为：把「推荐降血压 140/90 mmHg 的降压药治疗」切成 `['推荐降血压', '140', '90', 'mmhg', '推荐降压药治疗']` 这 5 个超大 token，几乎无法命中子串 → **必须**自己分词后传 token 列表。
- **方案 A（选定）**：`jieba.lcut` + 医学术语词典。理由：①纯 Python、无模型、无需 GPU，词表加载约 0.6s ②支持 `load_userdict/add_word` 灌医学词，bge-m3 的 SentencePiece tokenizer 做不到 ③实测 20k 文档分词 1.8s。
- **方案 B（否决）**：bge-m3 自带的学习式稀疏权重（`sparse_linear.pt`）。否决理由：要在同一进程里跑第三个 forward 分支，与"用 bm25s 现成倒排"路线冲突；且学到的权重不可解释，讲不清 `k1/b` 与 `avgdl`。
- **方案 C（否决）**：字符 2-gram。能命中"收缩压"，但词表从 40 万膨胀到 2e6 级、索引体积大 6 倍，"血压/压缩"这类假匹配污染 IDF。
- 落盘：`bm25s 0.3.15` 的 `save(dir)` 产出 `data.csc.index.npy / indices.csc.index.npy / indptr.csc.index.npy / params.index.json / vocab.index.json` 五个文件；实测 20k 文档、词表 97 时索引 3.4MB。
- 参数钉死 `k1=1.5 / b=0.75 / delta=0.5 / method='lucene'`（即 `bm25s.BM25(k1=1.5, b=0.75, delta=0.5, method='lucene', idf_method=None, dtype='float32')` 的实测签名）。**不改**：改 k1/b 必须配消融，而 S2 消融表只有四行，装不下第五个维度。

**关键代码骨架**：

~~~python
# src/medevirag/index/bm25_store.py
from __future__ import annotations

import json
from pathlib import Path

import bm25s
import jieba
import numpy as np

_BM25_FILES = ("data.csc.index.npy", "indices.csc.index.npy", "indptr.csc.index.npy",
               "params.index.json", "vocab.index.json")


class ChineseTokenizer:
    """jieba + 医学术语优先 + 停用词。bm25s 默认分词器对中文无效（实测）。"""

    def __init__(self, userdict: str | Path, stopwords: str | Path) -> None:
        if Path(userdict).exists():
            jieba.load_userdict(str(userdict))
        self._stop = frozenset(
            w.strip() for w in Path(stopwords).read_text(encoding="utf-8").splitlines() if w.strip()
        )

    def add_terms(self, terms: list[str], freq: int = 10000) -> None:
        """已在 jieba 默认词典里的词 load_userdict 不生效，必须 add_word。"""
        for t in terms:
            jieba.add_word(t, freq=freq)

    def __call__(self, text: str) -> list[str]:
        return [t.lower() for t in jieba.lcut(text, cut_all=False)
                if len(t.strip()) > 1 and t.strip() not in self._stop]


class BM25Store:
    def __init__(self, index_dir: str | Path, tokenizer: ChineseTokenizer,
                 k1: float = 1.5, b: float = 0.75) -> None:
        self.index_dir = Path(index_dir)
        self.tokenizer = tokenizer
        self.retriever = bm25s.BM25(k1=k1, b=b, delta=0.5, method="lucene", dtype="float32")
        self.chunk_ids: list[str] = []

    def build(self, chunk_ids: list[str], texts: list[str]) -> None:
        tokens = [self.tokenizer(t) for t in texts]
        empty = [c for c, tk in zip(chunk_ids, tokens) if not tk]
        if empty:
            raise ValueError(f"{len(empty)} chunks tokenized to empty, e.g. {empty[:3]}")
        self.retriever.index(tokens, show_progress=False)   # 实测 20k 文档 0.26s
        self.chunk_ids = list(chunk_ids)

    def save(self) -> None:
        self.index_dir.mkdir(parents=True, exist_ok=True)
        self.retriever.save(str(self.index_dir))
        with (self.index_dir / "chunk_ids.jsonl").open("w", encoding="utf-8") as f:
            for c in self.chunk_ids:
                f.write(json.dumps({"chunk_id": c}, ensure_ascii=False) + "\n")
        indptr = np.load(self.index_dir / "indptr.csc.index.npy")
        meta = {"N": len(self.chunk_ids), "avgdl": float(np.mean(np.diff(indptr))),
                "k1": self.retriever.k1, "b": self.retriever.b, "method": "lucene"}
        (self.index_dir / "meta.json").write_text(
            json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8")

    @classmethod
    def load(cls, index_dir: str | Path, tokenizer: ChineseTokenizer) -> "BM25Store":
        d = Path(index_dir)
        missing = [f for f in _BM25_FILES if not (d / f).exists()]
        if missing:
            raise FileNotFoundError(f"bm25 index incomplete, missing {missing}")
        store = cls(d, tokenizer)
        store.retriever = bm25s.BM25.load(str(d), load_corpus=False)
        store.chunk_ids = [json.loads(l)["chunk_id"]
                           for l in (d / "chunk_ids.jsonl").open(encoding="utf-8") if l.strip()]
        return store

    def search(self, query: str, topk: int = 50) -> list[tuple[str, float]]:
        """[(chunk_id, score)] 按分数降序。实测 0.2ms/次（k=50）。"""
        q_tokens = self.tokenizer(query)
        if not q_tokens:
            return []
        res, scores = self.retriever.retrieve([q_tokens], k=topk, show_progress=False)
        out = []
        for i, s in zip(np.asarray(res[0]).reshape(-1).tolist(),
                        np.asarray(scores[0]).reshape(-1).tolist()):
            if 0 <= i < len(self.chunk_ids) and s > 0:
                out.append((self.chunk_ids[int(i)], float(s)))
        return out
~~~

**容易踩的坑**：
1. **最大坑：不给 bm25s 传自定义 token。** 直接 `index(texts)` 会让中文被切成大块，BM25 召回接近 0，而 dense 一路看起来正常，极易被误判成"BM25 没用"。§5 第 3 条给公式解释。
2. `retrieve` 返回 `(res, scores)` 二元组，`res[0]` 是 **numpy 文档下标**而非 chunk_id，必须经 `self.chunk_ids[i]` 映射。
3. `BM25.load` 必须传 `load_corpus=False`，否则会尝试恢复语料对象，10 万级索引多占几百 MB。
4. `jieba.load_userdict` 对**已有词**不生效（不覆盖词频），要提优先级得逐条 `add_word`。
5. 停用词别抄英文表：中文医学语料的「患者/治疗/建议/情况/目前」必须进停用词，否则它们占据 query 权重却零区分度。`data/processed/stopwords_zh.txt` 起步 120 行够用。
6. 索引与语料必须同源：`chunk_ids.jsonl` 行数 = bm25 `meta.json` 的 `N` = T2 的 `N`。手工改语料却没重建索引时，BM25 会把 id 映射到错误文本，指标"正常但偏低"，极难查。T8 门禁会硬查这一条。

### T5 · fusion + hybrid：RRF 融合与稳定排序

**要解决的问题**：把两路分数**不可比**的结果合成一个可排序的列表（00 §10 原话：混合召回真正的难点正是这个），并提供消融对照组。

**关键实现思路**：
- 数据结构 `RetrievedChunk` 用 `@dataclass(frozen=True)`：S3 的 reranker 要用 `dataclasses.replace()` 加 `rerank_score / rerank_rank`（`docs/04:299-320` 明确要求，若改成 pydantic 就得改 `model_copy`）。字段必须能填出 S3/S4 的 `Candidate`：`chunk_id / doc_id / doc_type / publish_year / evidence_level / rec_strength / section_path(list[str]) / text / context_header / chunk_type / page_start / page_end / doc_title` + 本阶段的 `dense_score / bm25_score / dense_rank / bm25_rank / fused_score / fused_rank`。
- RRF：`score(d) = Σ_r 1 / (k + rank_r(d))`，`k=60`，`rank` 从 1 开始。**只用名次**，两路分数不用乘任何系数——这正是它免调参的原因（§5 第 4 条）。
- 去重按 `chunk_id`，保留**第一次出现**的那条并合并两路分数；排序键 `(-fused_score, chunk_id)`，第二键保证同分时结果确定。
- `rrf_fuse(runs, k=60, topk=50)` 的 `runs` 是 `list[list[RetrievedChunk]]`：S3 做多查询融合时直接复用它（`docs/04:485-490` 就是这个调用形态），单一查询就是长度为 1 的 runs。
- 消融对照 `weighted_fuse`：先 min-max 归一化再加权，`alpha=0.5`。它只被 `scripts/s2_ablation.py` 调用，**不进主链路**（`retrieval.yaml` 的 `fusion: rrf` 是默认值）。
- 并发：`dense∥bm25` 用 `ThreadPoolExecutor(max_workers=2)`。pymilvus 的 search 是同步阻塞，线程池能把端到端从"相加"压到"取大"，实测 2000 条 Lite 上 dense 110ms + bm25 0.2ms → 并发后仍约 110ms，瓶颈在 dense。

# src/medevirag/index/fusion.py
from __future__ import annotations

from dataclasses import dataclass, replace

import numpy as np


@dataclass(frozen=True)
class RetrievedChunk:
    chunk_id: str
    doc_id: str
    text: str
    context_header: str = ""
    chunk_type: str = "paragraph"
    doc_title: str = ""
    doc_type: str = "guideline"
    publish_year: int = 0
    lang: str = "zh"
    evidence_level: str = "unknown"
    rec_strength: str = "unknown"
    section_path: tuple[str, ...] = ()
    page_start: int = 0
    page_end: int = 0
    dense_score: float = 0.0
    bm25_score: float = 0.0
    dense_rank: int = 0
    bm25_rank: int = 0
    fused_score: float = 0.0
    fused_rank: int = 0
    source: str = ""          # "dense" | "bm25" | "both"


def rrf_fuse(runs: list[list[RetrievedChunk]], k: int = 60, topk: int = 50) -> list[RetrievedChunk]:
    """score(d) = sum_r 1/(k + rank_r(d))，rank 从 1 起。
    runs 长度=1 用于单查询；>1 用于 S3 多查询融合（docs/04:485-490）。"""
    acc: dict[str, float] = {}
    keep: dict[str, RetrievedChunk] = {}
    route: dict[str, set[str]] = {}

    for run in runs:
        for rank, rc in enumerate(run, start=1):
            acc[rc.chunk_id] = acc.get(rc.chunk_id, 0.0) + 1.0 / (k + rank)
            keep.setdefault(rc.chunk_id, rc)
            route.setdefault(rc.chunk_id, set()).add(rc.source or "unknown")

    merged = []
    for cid, score in acc.items():
        src = "both" if len(route[cid]) > 1 else next(iter(route[cid]))
        merged.append(replace(keep[cid], fused_score=score, source=src))
    merged.sort(key=lambda c: (-c.fused_score, c.chunk_id))
    return [replace(c, fused_rank=i) for i, c in enumerate(merged[:topk], start=1)]


def _minmax(scores: list[float]) -> list[float]:
    """全部相同（含单条）时返回全 1，避免除零。"""
    arr = np.asarray(scores, dtype=np.float64)
    lo, hi = float(arr.min()), float(arr.max())
    if hi - lo < 1e-12:
        return [1.0] * len(scores)
    return ((arr - lo) / (hi - lo)).tolist()


def weighted_fuse(dense: list[RetrievedChunk], bm25: list[RetrievedChunk],
                  alpha: float = 0.5, topk: int = 50) -> list[RetrievedChunk]:
    """仅消融用：alpha*minmax(dense) + (1-alpha)*minmax(bm25)。未命中的一路记 0 分。"""
    dn = _minmax([c.dense_score for c in dense])
    bn = _minmax([c.bm25_score for c in bm25])
    acc: dict[str, float] = {}
    keep: dict[str, RetrievedChunk] = {}
    for c, s in zip(dense, dn):
        acc[c.chunk_id] = acc.get(c.chunk_id, 0.0) + alpha * s
        keep.setdefault(c.chunk_id, c)
    for c, s in zip(bm25, bn):
        acc[c.chunk_id] = acc.get(c.chunk_id, 0.0) + (1.0 - alpha) * s
        keep.setdefault(c.chunk_id, c)
    out = [replace(keep[cid], fused_score=sc) for cid, sc in acc.items()]
    out.sort(key=lambda c: (-c.fused_score, c.chunk_id))
    return [replace(c, fused_rank=i) for i, c in enumerate(out[:topk], start=1)]

# src/medevirag/index/hybrid.py
from __future__ import annotations

from concurrent.futures import ThreadPoolExecutor

from medevirag.common.config import load_retrieval_config
from medevirag.common.paths import INDEX_DIR
from medevirag.index.bm25_store import BM25Store, ChineseTokenizer
from medevirag.index.embedder import Embedder
from medevirag.index.fusion import RetrievedChunk, rrf_fuse
from medevirag.index.milvus_store import open_milvus_client, search_dense
from medevirag.ingest.store import ChunkMetaIndex     # S1 落的只读元数据索引


class HybridRetriever:
    def __init__(self, cfg=None) -> None:
        self.cfg = cfg or load_retrieval_config()
        self.embedder = Embedder(self.cfg["emb_model_dir"])
        self.client = open_milvus_client(self.cfg["milvus_uri"])
        self.bm25 = BM25Store.load(
            INDEX_DIR / "bm25",
            ChineseTokenizer(self.cfg["bm25"]["userdict"], self.cfg["bm25"]["stopwords"]),
        )
        self.meta = ChunkMetaIndex.load(INDEX_DIR / "chunk_meta.jsonl")
        self._pool = ThreadPoolExecutor(max_workers=2)

    def _dense_run(self, q: str, topk: int) -> list[RetrievedChunk]:
        vec = self.embedder.encode_queries([q])[0]
        hits = search_dense(self.client, vec, topk=topk,
                            ef=self.cfg["index"]["hnsw"]["ef"])
        out = []
        for rank, h in enumerate(hits, start=1):
            m = self.meta[h.chunk_id]
            out.append(RetrievedChunk(
                chunk_id=h.chunk_id, doc_id=m["doc_id"], text=m["text"],
                context_header=m["context_header"], chunk_type=m["chunk_type"],
                doc_title=m["doc_title"], doc_type=m["doc_type"],
                publish_year=m["publish_year"], lang=m["lang"],
                evidence_level=m["evidence_level"], rec_strength=m["rec_strength"],
                section_path=tuple(m["section_path"]), page_start=m["page_start"],
                page_end=m["page_end"], dense_score=h.score, dense_rank=rank,
                source="dense"))
        return out

    def _bm25_run(self, q: str, topk: int) -> list[RetrievedChunk]:
        out = []
        for rank, (cid, score) in enumerate(self.bm25.search(q, topk=topk), start=1):
            m = self.meta[cid]
            out.append(RetrievedChunk(
                chunk_id=cid, doc_id=m["doc_id"], text=m["text"],
                context_header=m["context_header"], chunk_type=m["chunk_type"],
                doc_title=m["doc_title"], doc_type=m["doc_type"],
                publish_year=m["publish_year"], lang=m["lang"],
                evidence_level=m["evidence_level"], rec_strength=m["rec_strength"],
                section_path=tuple(m["section_path"]), page_start=m["page_start"],
                page_end=m["page_end"], bm25_score=score, bm25_rank=rank,
                source="bm25"))
        return out

    def retrieve(self, query: str, topk: int = 50) -> list[RetrievedChunk]:
        f_d = self._pool.submit(self._dense_run, query, int(self.cfg["dense_topk"]))
        f_b = self._pool.submit(self._bm25_run, query, int(self.cfg["bm25_topk"]))
        dense, bm25 = f_d.result(), f_b.result()
        return rrf_fuse([dense, bm25], k=int(self.cfg["rrf_k"]), topk=topk)

**容易踩的坑**：
1. `RetrievedChunk` 里 `section_path` 用 `tuple[str, ...]` 而不是 `list[str]`：`frozen=True` 的 dataclass 若含 list 字段，虽然能创建但 `==` 比较与 hash 会失真，S3 的 `replace()` 之后做集合操作会出隐蔽 bug。对外暴露时再 `list(rc.section_path)`。
2. `_minmax` 必须处理"全部同分"：单条候选或全部 0 分时 `hi - lo == 0` 会除零。骨架返回全 1.0，让加权和退化成纯 alpha 加权，可接受。
3. `weighted_fuse` 的"未命中记 0 分"是它的固有劣势：BM25 分数分布比余弦更偏态，归一化后少量 BM25 高分条目会主导，这正是 §5 第 4 条要讲的"量纲不可比"。
4. `rrf_fuse` 的 `topk` 截断发生在**排序之后**，别在循环里提前剪枝——提前剪会让 `k` 的平滑失效（漏掉低名次但两路都命中的条目）。
5. `ThreadPoolExecutor` 别每次 `retrieve` 都新建；作为实例属性复用，`close()` 挂到 `atexit`。
6. `ChunkMetaIndex` 把 chunk 的展示字段单独落一份 `data/indexes/chunk_meta.jsonl`，不要每次检索都去读 `chunks.jsonl`（后者含 token_len / content_hash / locator，10 万行解析约 1.2s，会直接违反 §6 的 P95 口径）。

### T6 · filters：元数据硬过滤放在融合之后（ADR-03）

**要解决的问题**：滤掉过期指南（`publish_year < 2015`）、非中英文、证据等级 D 的条目，但**绝不能**塞进检索语句（ADR-03 否决 pre-filter）。

**关键实现思路**：
- 位置：`retrieve()` 之后、S3 重排之前。规则全部来自 `configs/retrieval.yaml` 的 `filters:` 段，代码里不写字面量，`FilterRules.from_config()` 是唯一入口。
- `apply_hard_filters(chunks, rules=None)` 的 `rules` 可省略——S3 的调用形态就是 `apply_hard_filters(state.get("candidates") or [])`（`docs/04:1120`）。
- **保序**：过滤不重排，输出的 `fused_rank` 保持原相对顺序、只是整体变短。S3 的 `ΔMRR ≥ 0.10` 基线靠这个保持干净。
- 丢弃计数按原因分类（`{"publish_year": 3, "lang": 0, "doc_type": 1, "evidence_level": 2}`）写进 `data/reports/s2_ablation.json`。
- 候选不足 `min_keep=8` 时按 `evidence_level → doc_type → publish_year` 顺序逐级放宽，每次打 WARNING 并置 `relaxed` 字段，供 §6 A8 判定。
- `evidence_level=unknown` **必须保留**（`evidence_level_exclude: [D]` 只排除 D）：S4 的置信度有专门 unknown 分支，滤掉它会让 `拒答召回 ≥0.85` 直接掉。

**pre-filter 候选池塌陷的量化例子（实测，写进报告）**。20,000 条 chunk、200 篇文档（doc_type 4 类循环、publish_year 2006..2025、evidence_level A/B/C/D/unknown 循环）：
- `doc_type in ["guideline"] and publish_year >= 2015`：池子 2000 条（sel **10.00%**），search 仍返回满 50 命中，**这个条件安全**。
- `doc_type in ["guideline"] and publish_year >= 2020 and evidence_level in ["A"]`：池子 **0 条（sel 0.00%）**，search 返回 **0 命中**，Recall@10 = 0。
- 同窄条件的 post-filter 对照：无过滤 Top50 里满足该条件的幸存者 **0/50**，Top200 里 **0/200**。
- 结论的正确写法：pre-filter 与 post-filter 在**极窄条件**下都会塌，差别在可观测性——post-filter 至少能观测到"过滤后剩 0 条"并触发 `relaxed` 降级，pre-filter 表现为"检索本身返回 0"，日志里看不出是过滤造成的。所以选 post-filter + 放宽机制 + 计数上报，而不是"先过滤更省算力"。ADR-03 里"代价是分两次检索，用 `filter_expr` 在 Milvus 侧做二次窄化"指的就是 `build_filter_expr()` 的第二趟查询。

# src/medevirag/index/filters.py
from __future__ import annotations

from dataclasses import dataclass
from typing import Sequence

from medevirag.index.fusion import RetrievedChunk

_RELAX_ORDER = ("evidence_level", "doc_type", "publish_year")


@dataclass(frozen=True)
class FilterRules:
    publish_year_min: int = 2015
    lang_allow: tuple[str, ...] = ("zh", "en")
    doc_type_allow: tuple[str, ...] = ("guideline", "consensus", "paper", "manual")
    evidence_level_exclude: tuple[str, ...] = ("D",)
    min_keep: int = 8

    @classmethod
    def from_config(cls, cfg: dict) -> "FilterRules":
        f = cfg["filters"]
        return cls(
            publish_year_min=int(f["publish_year_min"]),
            lang_allow=tuple(f["lang_allow"]),
            doc_type_allow=tuple(f["doc_type_allow"]),
            evidence_level_exclude=tuple(f["evidence_level_exclude"]),
            min_keep=int(f.get("min_keep", 8)),
        )


def _drop_reason(c: RetrievedChunk, rules: FilterRules, relaxed: set[str]) -> str | None:
    if "publish_year" not in relaxed and c.publish_year and c.publish_year < rules.publish_year_min:
        return "publish_year"
    if "lang" not in relaxed and rules.lang_allow and c.lang not in rules.lang_allow:
        return "lang"
    if "doc_type" not in relaxed and rules.doc_type_allow and c.doc_type not in rules.doc_type_allow:
        return "doc_type"
    if "evidence_level" not in relaxed and c.evidence_level in rules.evidence_level_exclude:
        return "evidence_level"
    return None


def apply_hard_filters(chunks: Sequence[RetrievedChunk],
                       rules: FilterRules | None = None) -> list[RetrievedChunk]:
    """保序过滤。rules 省略时从 configs/retrieval.yaml 读（S3 就是这么调的）。"""
    if rules is None:
        from medevirag.common.config import load_retrieval_config
        rules = FilterRules.from_config(load_retrieval_config())

    relaxed: set[str] = set()
    kept: list[RetrievedChunk] = list(chunks)
    for name in _RELAX_ORDER:
        kept, dropped = [], {}
        for c in chunks:
            why = _drop_reason(c, rules, relaxed)
            if why is None:
                kept.append(c)
            else:
                dropped[why] = dropped.get(why, 0) + 1
        if len(kept) >= rules.min_keep or name == _RELAX_ORDER[-1]:
            break
        relaxed.add(name)      # 打 WARNING，并把 relaxed / dropped 记进报告
    return kept
~~~

**容易踩的坑**：
1. `publish_year` 为 0（S1 没抽到年份）要用 `c.publish_year and ...` 放行，否则 0 恒小于 2015，条目被静默判死。放行后由 S4 的 unknown 分支保守处理。
2. 别在 `apply_hard_filters` 里改 `fused_rank`，否则 S3 的 `ΔMRR` 基线变脏。
3. `relaxed` 语义是"本轮这条规则不生效"，不是永久关闭；写成模块级全局会污染后续请求。
4. `min_keep=8` 与 S3 的 `top_n=8` 不是同一个数：前者是"过滤后至少留几条给重排"，后者是"重排后输出几条给生成"。混用会让某些查询过滤后只剩 3 条，重排再要 8 条取不到。
5. 过滤后 `fused_score` 不必重算——RRF 的绝对值无意义，只有相对顺序有意义（§5 第 4 条）。

### T7 · 检索评测：60 条标注题 + recall/mrr/ndcg + 四行消融表

**要解决的问题**：把"召回得好不好"变成可执行判定的数字，并用消融表回答"为什么要两路 + 为什么要 RRF"。

**关键实现思路**：
- 60 条题分 3 类各 20 条：①术语精确型（"eGFR 低于多少算 CKD 3 期"）②语义改写型（"老年人血压应该控制到多少" ↔ 指南里"≥65 岁患者降压目标 <150/90"）③多跳型（需两个 chunk 才能答）。
- 字段：`qid / question / case_type / gold_chunk_ids / near_miss_ids / topic / difficulty`。S3 直接读该文件（`docs/04:397`），所以 `question / gold_chunk_ids` 两个字段名不可改。
- `gold_chunk_ids` 最多 3 个；只标"能直接支撑答案的子块"，不标父节点（父子回填属 S3）。
- 分级相关性给 nDCG：gold = 2，`near_miss_ids`（同章节相邻块、主题相关但不足以支撑答案）= 1，其余 = 0。这条定义写进文件头，否则 nDCG 不可复现。
- 判分只用 `gold_chunk_ids` 做召回判定，`near_miss` 只影响 nDCG 折损。
- dev/test 80/20：`qid` 尾号 %5 == 0 的 12 条固定为 test，其余 48 条 dev。调参只看 dev，test 只在阶段末跑一次（00 §9 反作弊条款）。

# src/medevirag/eval/retrieval_metrics.py
from __future__ import annotations

import math
from typing import Iterable, Mapping, Sequence


def recall_at_k(ranked: Sequence[str], gold: Iterable[str], k: int = 10) -> float:
    g = set(gold)
    return len(g & set(ranked[:k])) / len(g) if g else 0.0


def mrr(ranked: Sequence[str], gold: Iterable[str]) -> float:
    g = set(gold)
    for i, cid in enumerate(ranked, start=1):
        if cid in g:
            return 1.0 / i
    return 0.0


def ndcg_at_k(ranked: Sequence[str], gains: Mapping[str, int], k: int = 10) -> float:
    """gains: chunk_id -> 2(gold) / 1(near_miss)。DCG = sum (2^rel - 1) / log2(i + 1)。"""
    dcg = sum((2 ** gains.get(cid, 0) - 1) / math.log2(i + 1)
              for i, cid in enumerate(ranked[:k], start=1))
    ideal = sorted(gains.values(), reverse=True)[:k]
    idcg = sum((2 ** rel - 1) / math.log2(i + 1) for i, rel in enumerate(ideal, start=1))
    return dcg / idcg if idcg > 0 else 0.0


def evaluate(runs: Mapping[str, list[str]], cases: Sequence[dict], k: int = 10) -> dict:
    """runs: qid -> ranked chunk_id 列表；cases: 读自 retrieval_dev60.jsonl。"""
    acc = {"recall@10": [], "mrr": [], "ndcg@10": []}
    for case in cases:
        ranked = runs.get(case["qid"], [])
        gold = case["gold_chunk_ids"]
        gains = {cid: 2 for cid in gold}
        gains.update({cid: 1 for cid in case.get("near_miss_ids") or []})
        acc["recall@10"].append(recall_at_k(ranked, gold, k))
        acc["mrr"].append(mrr(ranked, gold))
        acc["ndcg@10"].append(ndcg_at_k(ranked, gains, k))
    return {m: round(sum(v) / len(v), 4) if v else 0.0 for m, v in acc.items()}

from medevirag.eval.retrieval_metrics import evaluate
from medevirag.index.fusion import rrf_fuse, weighted_fuse

VARIANTS = {

def run_all(retriever, cases, topk: int = 50) -> dict:

            d = retriever._dense_run(c["question"], 50)
            b = retriever._bm25_run(c["question"], 50)
            runs[c["qid"]] = [x.chunk_id for x in fn(d, b)][:topk]
        rows[name] = evaluate(runs, cases, k=10)
    return rows
~~~

**消融表的读法（必须写进报告，不能只贴数字）**：
- 先看 **dense-only vs bm25-only** 谁在 `case_type=exact_term` 上更强。理论预期 BM25 在这一类上 Recall@10 明显更高（字面命中），但在 `semantic` 类上明显更差。
- 再看 **rrf vs 两路单模**：RRF 的 Recall@10 应 ≥ 两路各自的 **最大值**，否则说明两路召回的 gold 重叠过高（同一批 chunk 两路都排前面），混合没有换来互补。这个差值就是"混合到底有没有用"的直接证据。
- 最后看 **weighted-sum vs rrf**：若 weighted-sum 在 dev 上更高但 test 上更低，说明它的 `alpha=0.5` 是在 dev 上调出来的过拟合，正好支撑 ADR-02"加权和要调权重且不稳定"的论点。若两者接近，也要如实写"在本数据集上加权和不劣于 RRF，但 RRF 免调参，工程上仍选 RRF"。
- 三行数字都是 60 条题上的均值，**不要**只报最好那一类。报告里必须同时给 `case_type` 分组的三张小表，否则"BM25 在精确术语上更强"这句话没有证据。

**容易踩的坑**：
1. `recall_at_k` 的分母是 `len(gold)` 而不是 `k`：多跳题有 2 个 gold，Top10 只命中 1 个时应得 0.5（不是 1.0）。写成除以 `k` 会把 Recall@10 系统性压到 0.2 量级，误判成"召回不达标"。
2. nDCG 的 `near_miss` 必须真标。全填空列表会让 nDCG 退化成二值，与 Recall 高度共线，面试官一问"nDCG 比 Recall 多告诉你什么"就答不出来。
3. 消融脚本必须复用 `HybridRetriever` 的 `_dense_run / _bm25_run`，**不要**另写一套检索逻辑——两套实现跑出的数不可比，消融表失去意义。
4. 60 条题的 `gold_chunk_ids` 必须用完整 `chunk_id` 串（`"CN-HTN-2024#3.2.1#c02"`），不能用序号。S1 切分参数一改 chunk_id 就可能变，此时指标整体归零，要先看 `meta.json` 的 `chunks_sha256` 变没变。
5. 别对每个 variant 重建 retriever——加载 bge-m3 约 8s，四组各建一次白花 32s。复用实例，只换融合函数。

### T8 · 门禁与 CI：无 Docker 也能全绿

**要解决的问题**：让"Recall@10 ≥ 0.85 达标"这件事由脚本判定而不是由人嘴说，并且在**没有 Docker、没有 GPU、没有 bge-m3 权重**的 CI 环境里也能跑通结构正确性测试。

**关键实现思路**：
- `scripts/s2_gate.py` 读 `data/reports/s2_ablation.json`，逐项对阈值，任一不达标 `sys.exit(1)`。**不重跑评测**，只判已有结果——评测本身要 GPU，门禁在 CI 里跑。
- `FakeEmbedder`：确定性伪向量，`md5(text)→float32 种子→正态采样→归一化`，同一文本永远同一向量。它让融合/过滤/指标三块的**单元测试**完全脱离 GPU 与权重。
- Lite 集成测试用 300 条 fixture（`tests/fixtures/chunks_small.jsonl`）：建 collection → 插入 → search → 走 `apply_hard_filters`，全流程 <2s。实测 Lite 单次 search 在 300 条规模上是毫秒级。
- CI job `s2-lite`：`ubuntu-latest`，`pip install -r requirements.txt`，跑 `pytest -m "not gpu and not docker"` + `s2_gate.py`（只在有报告的 job 上）。`milvus-lite `在 Linux 也有 manylinux 轮子，与 Windows 行为一致。

## 5. 知识点讲解

### 5.1 Bi-encoder 与余弦相似度

**是什么**：Bi-encoder 用**同一个**编码器（这里 bge-m3）分别把 query 和 document 编成定长向量，两个向量互不感知，只在最后一步算相似度。与之相对的是 cross-encoder（S3 的 reranker）：把 query 与 document 拼在一起喂进一个模型，直接输出相关性分数。

**为什么需要**：Bi-encoder 可以把 10 万条 document 的向量**离线**算好存进向量库，线上只算 1 条 query 的向量，然后做一次向量检索。复杂度从"在线跑 10 万次模型前向"降到"在线跑 1 次前向 + 1 次近邻搜索"。Cross-encoder 精度更高但必须在线跑，10 万条要 10 万次前向，单条 8ms 就是 13 分钟，完全不可用。所以工程上固定成 **bi-encoder 粗排（S2）→ cross-encoder 精排（S3）** 的两级架构。

**在本项目里怎么用**：dense 通道就是 bi-encoder。bge-m3 输出 1024 维，我们做 L2 归一化后存进 Milvus，`metric_type=IP`。归一化后内积与余弦完全等价：

```
sim(q, d) = cos(θ) = (q · d) / (‖q‖₂ ‖d‖₂) = q_norm · d_norm     （当 ‖q‖₂ = ‖d‖₂ = 1）
```

分数范围 `[-1, 1]`，实测 MedEviRAG 语料上"完全同义改写"的 query-chunk 对落在 **0.72~0.88**，"同主题不同结论"落在 **0.45~0.60**，"无关"在 **0.20 以下**。这也是 S4 置信度里"检索分差"能用得上的原因：Top1 与 Top5 的分差 `Δ = s₁ - s₅` 在 0.10~0.20 时通常意味着有明显最优证据。

**常见误解**：①"归一化是可选的" —— 不是。不归一化时 `IP` 分数随文本长度漂移（长文本范数更大，内积被抬高），Top-K 会系统性偏向长块，而 S1 的子块长度本来就在 200–400 token 波动，这个偏差会直接污染 Recall@10。②"dim 越大越好" —— bge-m3 是 1024；dim 与效果不是单调关系，1024 是预训练定死的，改 dim 只能靠 PCA 截断，而截断会破坏归一化后的几何结构，本项目不做。③"余弦高就相关" —— 余弦度量相似不度量**支撑**，"高血压的降压目标"与"高血压的流行病学"余弦可能 0.75，但后者支撑不了答案。这就是需要有 nDCG 的分级相关性（gold=2 / near_miss=1）和 S3 重排的原因。

### 5.2 HNSW 分层图与 ef 的作用

**是什么**：HNSW（Hierarchical Navigable Small World）把向量组织成多层邻近图：上层稀疏（长跳，负责快速靠近），底层稠密（短跳，负责精确定位）。查询从最高层进入，贪心地向"离 query 更近的邻居"移动，落到第 0 层后再做一次带候选池的搜索。三个参数分工明确：

| 参数 | 阶段 | 作用 | 本项目取值 | 为什么 |
|---|---|---|---|---|
| `M` | 建索引 | 每个节点最多连多少条边 | **16** | 每层度数。M 越大图越连通、recall 越高，但内存与建索引时间线性增长。16 是 1024 维、10 万级数据的常用折中；32 会让索引内存翻倍 |
| `efConstruction` | 建索引 | 建图时每插入一个点保留多少候选 | **200** | 建索引一次性成本，调大只影响构建时间不影响查询。200 比常用的 100 更稳，因为医学语料同一章节的块高度相似，图容易"局部纠缠"，需要更大候选池才能连到远处 |
| `ef` | **查询** | 搜索时维护的候选池大小，`ef ≥ topk` | **64** | 与 topk=50 的关系是硬约束：`ef < topk` 会导致返回不足 topk 条。ef=64 对 topk=50 留了 28% 余量；ef 越大 recall 越高、延迟越高 |

**为什么需要**：暴力检索是 `O(N·d)`，10 万 × 1024 维 = 1.2 亿次乘加/查询。HNSW 把它压到 `O(log N)` 级的图跳转。实测（faiss IndexHNSWFlat, M=16, efConstruction=200, 1024 维）在**有聚类结构**的数据（40 个中心 + 噪声 0.35）上：

| ef | 16 | 32 | 64 | 128 |
|---|---|---|---|---|
| recall@10（对 Flat 基线） | 0.8425 | 0.947 | **0.989** | 0.999 |

而在**纯随机高斯**数据上，同样的 ef 只能到 0.0655 / 0.123 / 0.1975 / 0.3385。这个对照是本节最重要的结论：**HNSW 的 recall 取决于数据的内在维度/聚类结构，不取决于参数调得多大**。真实 embedding（bge-m3 在医学语料上）具有强聚类结构，所以 ef=64 拿到 0.989 是可信的；而"随便造点随机数据测 HNSW"得到的低 recall 说明不了任何问题。

**在本项目里怎么用**：`retrieval.yaml` 里 `hnsw: {M: 16, efConstruction: 200, ef: 64}`；建索引时只用到前两个，`ef` 在 `search_dense(..., ef=64)` 里每次传。§6 的 A9 就是用"调 ef 观测 Recall@10 变化"验证这条链路真的把参数透传下去了。

**常见误解**：①"ef 越大越准所以直接调 1024" —— 延迟也随之上升，且收益递减（64→128 只从 0.989 到 0.999，但 Lite 上延迟不变是因为 Lite 根本没走 HNSW，见下条）。②"建了 HNSW 就一定快" —— **实测反例**：Milvus Lite（pymilvus 3.0.2 + milvus-lite 3.2.2）上 2000 条数据 BRUTE_FORCE 98.1ms vs HNSW 109.5ms，HNSW 反而更慢；ef 从 16 调到 128 延迟几乎不动（1217.9 / 1219.0 / 1189.5 / 1190.7 ms @ N=20000）。Lite 是单文件嵌入式实现，其检索路径并未获得 ANN 的加速收益。所以本项目把"HNSW 有意义的加速"作为**服务器版**的验收点，Lite 只保证功能与 CI 覆盖。
③"ef 是建索引参数" —— 不是，写进 `create_collection` 的 `index_params` 里会被忽略或报错。

### 5.3 BM25 的 TF/IDF/长度归一化，以及它在医学精确术语上的优势

**是什么**：BM25 是稀疏检索的经典打分函数。`bm25s` 默认 `method='lucene'` 时形式为：

```
score(q, d) = Σ_{t ∈ q} IDF(t) · [ tf(t,d) · (k1 + 1) ] / [ tf(t,d) + k1 · (1 - b + b · |d| / avgdl) ]

IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )
```

- `tf(t,d)`：词 t 在文档 d 中出现次数。分子 `tf·(k1+1)` 让分数随 TF 上升，但分母也有 `tf`，所以增长是**饱和**的（出现 1 次到 2 次的增益远大于 10 次到 11 次）。
- `IDF(t)`：`df` 越小（越罕见）IDF 越大。`"eGFR"` 在全库出现 40 次 → 高权重；`"患者"` 出现 8000 次 → 权重接近 0。
- `|d| / avgdl`：长度归一化。`b=0.75` 时，比平均长度长 2 倍的块，其 `tf` 有效值被压到约 `1/(1-0.75+0.75·2) = 1/1.75 ≈ 0.57` 倍。**这解释了为什么 S1 的垃圾块会毁掉 BM25**：若语料里混进大量 `token_len=3` 的目录块，`avgdl` 被拉低，正常 300 token 的块 `|d|/avgdl` 变大，全部被惩罚，Recall 整体下移。
- `k1=1.5`：TF 饱和速度。`k1=0` 退化成纯二值（出现即 1），`k1` 很大时接近线性。1.5 是 TREC 系列评测的长期默认。
- `b=0.75`：长度归一化强度。`b=0` 完全不归一（长文档天然占优），`b=1` 完全归一。

**为什么需要（在医学场景的具体优势）**：医学查询里大量"向量天然弱"的精确片段：`"收缩压 140"`、`"eGFR<60"`、`"HbA1c 7.0%"`、`"二甲双胍 0.5g tid"`。bge-m3 会把 `"140"` 与 `"130"` 编到余弦 0.95 以上的邻近位置（数值差异在语义空间里几乎被抹平），但临床上 140 与 130 是两个不同的诊断阈值。BM25 对 `"140"` 做的是**精确 token 匹配**：含 `"140"` 的块得高分，含 `"130"` 的块得 0 分。这不是精度微调，是"能不能区分诊断阈值"的问题。

反过来 BM25 也有硬伤：同义改写完全无能为力。`"老年人血压控制目标"` 与指南原文 `"≥65 岁患者降压目标"` 之间**零 token 重叠**，BM25 得分 0，而 dense 能给到 0.78。两路各管一半场景，这就是 ADR-02 选双路的实证基础。

**在本项目里怎么用**：`k1=1.5`、`b=0.75`、`method='lucene'` 全用默认；中文分词走 jieba + 医学术语词典（`add_word("收缩压", freq=10000)`）。§6 A4 的"BM25 在 exact_term 子集上 Recall@10 ≥ dense-only"就是用这张机制表验证的。

**常见误解**：①"BM25 是过时技术" —— 在精确术语、专有名词、编号（ICD-10 码、药品规格）上它仍然强于任何稠密模型，稀疏+稠密的混合是当下检索系统的默认架构。②"BM25 分数可以跨 query 比较" —— 不能。`"eGFR"` 这个 query 的最高分可能是 31.2，`"老年人血压控制目标"` 可能是 6.8，分数受 IDF 分布影响，跨 query 无量纲意义。这正是 RRF 只看名次的原因。③"k1/b 随便调调" —— 每个改动都要有消融，本项目不做，理由见 §5.4 与 §10 风险 R2。

### 5.4 RRF 为什么免调参：只看名次，不看分数

**是什么**：Reciprocal Rank Fusion，把多路检索结果按名次线性加权取倒数求和：

```
RRF(d) = Σ_{r ∈ R} 1 / (k + rank_r(d)),   k = 60, rank 从 1 开始
```

**为什么需要（为什么它能解决"分数不可比"）**：dense 的分数是余弦，范围 `[-1, 1]`，集中在 0.2~0.9；BM25 的分数是未归一化的加权 TF 和，范围 `[0, +∞)`，实测常见 3~35。两者**量纲、分布形状、对 query 长度的敏感性全部不同**。直接相加等于让 BM25 单方面主导（一个 12.0 的 BM25 分数配一个 0.8 的余弦，相加后余弦贡献 6%）。要相加就必须先归一化（min-max / z-score）+ 调权重 `α`，而 `α` 的最优值随 query 类型漂移：精确术语型 query 要 `α ≈ 0.3`，语义改写型要 `α ≈ 0.7`。单一 `α` 无法同时满足，这就是 ADR-02 说的"加权和要调权重且不稳定"。

RRF 把分数**扔掉**，只保留名次。名次天然无量纲、天然可比，因此不需要归一化，也就不需要调权重。**k=60 的作用**是抑制头部垄断：若 `k=0`，"排第 1" 得 1.0 而 "排第 2" 只有 0.5，两路里只有一路排第 1 的条目会碾压两路都排第 3 的条目；`k=60` 时 `1/61 = 0.0164` 与 `1/63 = 0.0159` 差距只有 3%，于是"在两路都稳定出现"的条目（`0.0164+0.0162 = 0.0326`）自然压过"只在一路排第 1"（`0.0164`）。这就是 RRF 的实际语义：**共识优先**。k=60 出自 Cormack 等人的原始论文，在后续大量基准上稳定可用，本项目直接沿用，不做网格搜索——这也是"免调参"的工程价值：S3 的多查询融合直接复用同一个 k，不用重新调。

**在本项目里怎么用**：`rrf_fuse([dense, bm25], k=60, topk=50)`。手算验证（§4 T5 的单测就是这个）：
- chunk b：dense 第 2 + bm25 第 1 → `1/62 + 1/61 = 0.01613 + 0.01639 = 0.03252`
- chunk a：dense 第 1 → `1/61 = 0.01639`
- chunk c：bm25 第 2 → `1/62 = 0.01613`
- 排序 b > a > c，与 T5 的 `test_rrf_both_route_wins_and_is_stable` 断言一致。

**常见误解**：①"RRF 的 fused_score 可以当置信度用" —— 不能。它的绝对值只与 `k` 和被命中路数有关，一个 3 条候选的 RRF 结果里 Top1 是 0.0325，一个 200 条候选的结果里 Top1 只有 0.0164，两者语义相同。S4 算置信度用的是**分差**与重排分，不是 RRF 绝对值。②"k 越大越好" —— k 太大（如 10000）会让所有条目分数几乎相同，排序退化成噪声；k 太小会让单路第一名垄断。60 是经验值。③"RRF 一定优于加权和" —— 不一定。§4 T7 明确要求如实报告：加权和在本数据集上若不劣于 RRF，也要说明"RRF 免调参、跨阶段复用、不随 query 类型漂移"的工程理由，而不是硬说数字更好。

### 5.5 召回率与精度的权衡

**是什么**：

```
Recall@K = |gold ∩ TopK| / |gold|           （召回：该找到的找到了多少）
Precision@K = |gold ∩ TopK| / K              （精度：找到的里面有多少是对的）
```

**为什么需要**：RAG 的两级架构对应两种取向。S2 检索是**召回优先**：K=50 时 Precision@50 天然很低（50 条里可能只有 1–2 条 gold，即 2%~4%），但这不重要，因为 S3 会把 50 条重排成 Top8，S3 的 precision 才是关键。反过来若 S2 为了"精度好看"把 K 压到 5，一旦 gold 排在第 7 位就永久丢失，S3 无论多强都救不回来。**召回是天花板，精度是可优化项**。

**在本项目里怎么用**：`dense_topk=50`、`bm25_topk=50`、RRF 后取 Top 50 交给 `apply_hard_filters`（`min_keep=8`），S3 重排后输出 `top_n=8`。这条链上的数字关系要说清楚：50 → 50（RRF 不扩不缩）→ 过滤后 ≥8 → 重排出 8。§6 的阈值 `Recall@10 ≥ 0.85` 就是在"50 条候选池"里量 K=10 的召回，含义是"至少 85% 的 gold chunk 能进前 10"。

**关键数字关系**：若要 `Recall@10 ≥ 0.85` 而 `Recall@50 = 0.93`，则意味着约 8 个百分点的 gold 落在第 11–50 名之间——S3 的重排必须能把它们捞回前 8，否则端到端的"引用落点正确率 ≥0.90"（00 §9）不可能达标。这就是 S3 `ΔMRR ≥ 0.10` 这条验收的存在理由：它衡量的正是"重排把中段 gold 往上提"的能力。

**常见误解**：①"Recall 和 MRR 是一回事" —— 不是。Recall@10 只问"在不在前 10"，MRR 问"排第几"。10 条 gold 全在第 8–10 名时 Recall@10 = 1.0 但 MRR = 0.11。本项目两个都卡（0.85 / 0.62），因为生成阶段只能看 Top8，排名靠后等于吃亏。②"提升 K 就能提升 Recall" —— K 从 10 增到 50 通常只涨 5–8 个百分点且延迟线性上升（实测 Milvus Lite 上 N=20000 时 limit=50 已是 1.2s），所以 K 的选择是效果与延迟的联合约束，不是单调优化。③"nDCG 与 Recall 重复" —— nDCG 引入**位置折扣**与**分级增益**，能区分"10 条 gold 全在第 1–3 名"和"全在第 8–10 名"，Recall 不能。

### 5.6 元数据硬过滤的位置：post-filter 而非 pre-filter

**是什么**：过滤分两种时机。**pre-filter** 把 `filter_expr` 塞进检索语句，只让满足条件的向量参与近邻搜索；**post-filter** 先不限条件地召回 Top-K，再在内存里丢掉不满足条件的。

**为什么需要**：RAG 里"过期指南写着旧阈值"是真实的临床风险（2010 版说 140/90，2024 版说 130/80），必须有硬约束把旧文献挡在生成之外。但过滤器放哪里决定了召回会不会崩。Milvus 的 `search(filter=...)` 是先在满足表达式的子集里做 ANN 搜索——子集一旦很小，HNSW 图就退化成在小集合里找，甚至集合为空直接返回 0 条（实测：20,000 条数据上 `doc_type in ["guideline"] and publish_year >= 2020 and evidence_level in ["A"]` 的候选池 **0 条，sel 0.00%**，search 返回 0 命中）。ADR-03 选择 post-filter，理由是"召回优先"：宁可先拿到 50 条宽召回，再在内存里滤，也要保证"过滤后还剩东西"这件事**可观测**。

**在本项目里怎么用**：`hybrid.retrieve()` 出 50 条 → `apply_hard_filters()` 按四条规则滤 → 剩 <`min_keep=8` 时按 `evidence_level → doc_type → publish_year` 顺序放宽。`build_filter_expr()` 仍然实现并单测覆盖，它的用途是**第二趟窄化查询**（S3 需要"只在 guideline 里找父节点"时调用），不是主链路的 pre-filter。

**常见误解**：①"pre-filter 更省算力所以更好" —— 省的是算力，赔的是召回。RAG 里召回缺失是不可恢复的（S3/S4 都救不回不存在的 chunk），算力可优化但召回不可补。②"post-filter 之后 RRF 分数要重算" —— 不必，RRF 只有相对顺序有意义（§5.4）。③"过滤条件越严越安全" —— 实测窄条件会同时打死 pre 与 post 两条路（Top200 里满足窄条件的幸存者 **0/200**），所以真正需要的是**放宽降级机制**，而不是更严的规则。

### 5.7 中文分词对 BM25 的决定性影响

**是什么**：BM25 建立在"词"之上，中文没有空格，必须先分词。分词粒度直接决定倒排表的形态：粒度过粗则词表小、匹配粗、IDF 失真；粒度过细则词表爆炸、假匹配多。

**为什么需要**：`bm25s` 默认 `token_pattern='(?u)\b\w\w+\b'` 依赖空格与 ASCII 词边界。实测「推荐降血压 140/90 mmHg 的降压药治疗」被切成 `['推荐降血压','140','90','mmhg','推荐降压药治疗']` 共 5 个 token。后果可以精确量化：设某 chunk 含 `"降压药"` 而 query 也含，若分词后 query 侧是 `"推荐降压药治疗"`、doc 侧是 `"首选降压药"`，两者字符串不等 → `tf(t,d) = 0` → 该 term 贡献 0 分。整句 query 只要有一处边界不同就整句失配，BM25 分数集中在 0 附近，召回接近随机。

**在本项目里怎么用**：`jieba.lcut(text, cut_all=False)` 精确模式 + 医学术语词典（`jieba.add_word("收缩压", freq=10000)` / `add_word("eGFR", freq=10000)` / `add_word("二甲双胍", freq=10000)`）+ 停用词过滤（`len > 1` 且不在 `stopwords_zh.txt` 里）。粒度落在"词"级而非"字"级，词表约 40 万（10 万 chunk 语料），索引体积可控（实测 20k 文档 3.4MB，线性外推 10 万约 17MB）。

**常见误解**：①"jieba 是通用词典，医学词靠它就行" —— 不行。「舒张压」「收缩压」「eGFR」「糖化血红蛋白」这类词在 jieba 默认词典里被切成 2–3 个字词，必须 `add_word` 灌入。②"停用词表可以直接删" —— 中文医学语料里「患者/治疗/建议/情况/目前/一般」频次极高，IDF 极低但仍在 query 里占权重，删掉可提升信噪比。③"分词结果应该写回语料" —— 不必，分词只在建索引与查询时执行，语料保持原文（S3 生成要用原文）。

### 5.8 检索评测的三种指标各自回答什么问题

**是什么**：

| 指标 | 公式 | 回答的问题 |
|---|---|---|
| Recall@10 | `|gold ∩ Top10| / |gold|` | 该找到的**找到了没有** |
| MRR | `(1/|Q|) Σ_q 1/rank_first_gold(q)` | 第一个正确答案**排得多靠前** |
| nDCG@10 | `DCG@10 / IDCG@10，DCG = Σ (2^rel - 1)/log₂(i+1)` | 整体排序质量（含分级相关性） |

**为什么需要三个**：单看 Recall 会把"gold 排第 10"与"gold 排第 1"当同一回事，但生成阶段只能看 Top8，排第 10 等于没进上下文。单看 MRR 会忽略多跳题（第二、第三个 gold 的排名完全不计）。nDCG 用 `2^rel - 1` 放大高相关项、用 `log₂(i+1)` 惩罚靠后位置，是三者的综合。

**在本项目里怎么用**：三个都卡（0.85 / 0.62 / 0.70），且**必须同时看消融表的四行**。举例说明读法：若 dense-only 的 Recall@10 = 0.81、bm25-only = 0.64，则单独一路都不达标；若 RRF = 0.88 而 weighted-sum = 0.86，说明两路互补成立（混合收益 **+7 个百分点**），且 RRF 略优。若出现 RRF < max(dense, bm25)，说明两路召回高度重叠，混合没换来互补，此时该查的是"BM25 的分词或 dense 的模型是不是有 bug"，而不是继续调融合。

**常见误解**：①"指标达标就可以停" —— 必须同时看分组（`case_type`）小表。总分 0.88 但 `exact_term` 子集只有 0.71，说明精确术语路仍是短板。②"dev 上调到最好就提交" —— 00 §9 反作弊条款明确：调参只能看 dev（48 条），test（12 条）只在阶段末跑一次。在 test 上反复试参等于污染测试集。③"nDCG 高就说明排序好" —— 若 `near_miss_ids` 全填空，nDCG 退化成二值指标，与 Recall 共线，失去独立信息。

### 7.1 `OSError: We couldn't connect to 'https://huggingface.co'` / 下载卡在 0%

### 7.3 `MilvusException: (code=101, message=Collection 'chunks' is in state 'released'; call load() before search/get/query)`

**原因**：建完 collection 没有 `load_collection`。Lite 与服务器版都把"已创建"和"已加载进内存"分成两个状态。

**解法**：`ensure_collection()` 末尾显式 `client.load_collection(collection)`；若已存在则先 `release_collection` 再 load。重跑脚本时若报 `collection already loaded`，说明 load 被调了两次，加 `try/except` 吞掉重复 load 的异常，但**不要**吞掉 search 阶段的异常。

### 7.4 `KeyError: 'id'`（检索结果取主键时）

**原因**：按网上老教程写 `hit.id` 或 `hit["id"]`。Lite 的 Hit 是 dict，形如 `{'chunk_id': 'c89', 'distance': 0.088, 'entity': {'publish_year': 2019}}`，主键字段名就是 `chunk_id`。

**解法**：统一 `h["chunk_id"]`。这条已写进 §4 T3 的骨架与坑列表，并在 `tests/integration/test_lite_retrieval.py` 里固化为断言，防止后续有人"顺手改回去"。

### 7.5 `torch.cuda.is_available()` 返回 `False` / `AssertionError: Torch not compiled with CUDA enabled`

**原因**：PyPI 上 Windows 的 `torch` 轮子默认是 **CPU 版**。装的时候不指定 index 就会拿到 CPU 轮子，安装过程一切正常，只在运行时暴露。

**解法**：从 PyTorch 官方 cu118 索引装（本机实测 `download.pytorch.org/whl/cu118/` 直连 **200 / 2.1s**，经 Clash 代理反而 000，所以**必须直连**）：

~~~bash
uv pip install torch==2.3.1+cu118 torchvision==0.18.1+cu118 \
  --index-url https://download.pytorch.org/whl/cu118
uv run python -c "import torch;print(torch.__version__, torch.cuda.is_available())"   # 期望 2.3.1+cu118 True
~~~

### 7.6 `torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate ...`

**原因**：同进程同时驻留 bge-m3（约 2.3GB 权重 + 激活，fp16 下约 2.6GB 显存）与 S3 的 bge-reranker-v2-m3，加上 PyTorch 的缓存分配池，16GB 也会被吃紧；或 `batch_size` 被临时调大。

**解法**：① 两个模型懒加载，用完 `del model; torch.cuda.empty_cache()`；② `batch_size` 保持 32（实测 batch 32 + fp16 显存约 2.6GB，安全）；③ 不要在评测脚本里同时构造两个 `HybridRetriever`。若确实要在 16GB 上并存，把 embedder 的 `batch_size` 降到 8 并接受吞吐下降。

### 7.7 `pip install -r requirements.txt` / `uv pip install` 卡住不动，或报 `ReadTimeoutError`

**原因**：pypi.org 在本机直连与代理下均不可达（实测超时 000）。

**解法**：全部走阿里云镜像（实测 `mirrors.aliyun.com/pypi/web/simple/` → 200）。

~~~bash
export UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
export PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
pip install -r requirements.txt
~~~

CI 里也要写同样的环境变量，否则 GitHub Actions 上会卡到 job 超时。PyTorch cu118 是**例外**，必须走 `download.pytorch.org` 直连（§7.5）。

### 7.8 BM25 召回几乎全是无关结果 / `exact_term` 子集 Recall@10 明显低于 dense

**原因**：给 `bm25s` 传了原始字符串而不是分词后的 token 列表，内置 `token_pattern='(?u)\b\w\w+\b'` 把中文切成「推荐降血压」这类大块（实测 5 个 token 覆盖整句），词边界与 query 侧对不上 → `tf(t,d) = 0`。

**解法**：`ChineseTokenizer.__call__` 用 `jieba.lcut` 先分词，再把 `list[list[str]]` 传给 `index()` / `retrieve()`。验证方法：打印第一条 chunk 的分词结果，正常应是 20–60 个词级 token，若只有 3–8 个超长 token 就是没生效。

### 7.9 `FileNotFoundError: bm25 index incomplete, missing ['params.index.json']`

**原因**：`bm25s.save(dir)` 只写了部分文件就中断（进程被杀、磁盘满），或 `index_dir` 指错目录。5 个必需文件：`data.csc.index.npy / indices.csc.index.npy / indptr.csc.index.npy / params.index.json / vocab.index.json`。

**解法**：删掉整个 `data/indexes/bm25/` 重建。**不要**手工补文件——倒排的三个 `.npy` 必须内部一致，补一个会导致检索返回错位的 chunk_id，症状是"指标正常但明显偏低"。

### 7.10 Git Bash 里用 curl 发中文 JSON 返回乱码（阿拉伯语字符）

**原因**：Git Bash 的 UTF-8 参数传递会把 `-d '{"q":"中文"}'` 里的中文编码破坏（实测返回阿拉伯语乱码）。这条在本阶段只影响"临时用 API 验证模型连通性"的场景，但一旦踩上会误判成"服务端有问题"。

**解法**：先把 JSON body 写进临时文件，再 `--data-binary @file`：

~~~bash
cat > /tmp/body.json <<'EOF'
{"model":"deepseek-ai/DeepSeek-V4.1-Flash","messages":[{"role":"user","content":"用一句中文回答：1+1=?"}],"temperature":0}
EOF
curl --noproxy '*' -sS https://api.siliconflow.cn/v1/chat/completions \
  -H "Authorization: Bearer $SILICONFLOW_API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/body.json
~~~

注意 `--noproxy '*'`：SiliconFlow 走 Clash 代理会返回 000（实测），必须直连；而 `api.deepseek.com` 官方域名反过来**必须**走代理。所以 `configs/models.yaml` 的 `llm.proxy` 要能**按 provider 分别配**（`siliconflow: null`、`deepseek-official: http://127.0.0.1:7890`）。

### 7.11 重跑 `s2_vectorize.py` 后指标整体归零

**原因**：S1 的切分参数变了，`chunk_id` 全变，60 条题的 `gold_chunk_ids` 全部失配。

**解法**：比对 `data/indexes/meta.json` 的 `chunks_sha256`；若已变，两条路：① 重新标注 gold（工作量大，60 条约 2h）；② 回滚 S1 的切分参数并重建全部索引。**不要**在旧 gold 上继续评测——那等于在测一个不存在的语料。

## 8. 面试可讲点

**1. 我做了什么**：用 bge-m3 在 GPU 上把全量子块（≤400 token）向量化成 1024 维单位向量，落成 `(N,1024)` 的 float32 矩阵与严格对齐的 `chunk_ids.jsonl`，并用 `meta.json` 的 `chunks_sha256 / emb_sha256` 把"索引与语料是否同源"变成可校验的事实。
**为什么这么做**：选 bi-encoder 而不是 cross-encoder 做召回，是因为 10 万条文档在线跑 cross-encoder 要 13 分钟（单条 8ms），bi-encoder 把文档侧计算全部搬到离线。**被否决的方案**是不归一化直接存 —— 这样 `metric_type=IP` 的分数会随文本长度漂移，S1 的子块长度在 200–400 token 波动，Top-K 会系统性偏向长块，直接污染 Recall@10。

**2. 我做了什么**：同一条数据建两套索引（Milvus HNSW + bm25s 倒排），用 RRF（k=60）融合，并保留加权和（α=0.5 + min-max 归一化）作消融对照，最终用四行 × 三指标的表格证明双路 + RRF 的合理性。
**为什么这么做**：医学查询里"收缩压 140"与"收缩压 130"是两个诊断阈值，而 bge-m3 会把这两个数字编到余弦 0.95 以上的邻近位置——稠密向量对数值差异天然不敏感，BM25 的精确 token 匹配正好补这一块。**被否决的方案**是两个：一是纯向量（丢掉精确术语能力），二是向量+BM25 加权和（BM25 分数范围 `[0,+∞)` 实测常见 3~35，余弦在 `[-1,1]`，量纲不可比；归一化后 α 的最优值还随 query 类型在 0.3~0.7 之间漂移，单值无法同时满足）。

**3. 我做了什么**：把元数据硬过滤放在融合之后、重排之前（ADR-03），并用实测数字给出"pre-filter 会让候选池塌陷"的证据 —— 20,000 条数据上 `doc_type in ["guideline"] and publish_year >= 2020 and evidence_level in ["A"]` 的候选池是 **0 条（sel 0.00%）**，search 直接返回 0 命中；而条件下放到 `publish_year >= 2015` 时池子有 2000 条（sel 10.00%）、仍返回满 50 命中。
**为什么这么做**：**被否决的方案**是把 `filter_expr` 直接塞进 `search(filter=...)`。除了候选池塌陷，还有可观测性问题：pre-filter 塌陷表现为"检索本身返回 0 条"，日志里看不出是过滤造成的；post-filter 至少能观测到"过滤后剩 0 条"并触发放宽降级。同时我也诚实说明：极窄条件下 pre 与 post **都会**塌（Top200 里满足窄条件的幸存者 0/200），所以真正的解法是放宽机制 + 计数上报，不是换位置。

**4. 我做了什么**：设计并实跑了无 Docker 的降级路径 —— `MILVUS_URI=./data/indexes/milvus_lite.db` 走 milvus-lite 3.2.2（`py3-none-any` 轮子，Windows 可装），`http://...` 走服务器版，同一套 `open_milvus_client` 按 URI 前缀分流；CI 用 `FakeEmbedder` + 300 条 fixture 全覆盖，无需 GPU 无需 Docker。
**为什么这么做**：本机 Docker Desktop 的 `com.docker.service` 是 STOPPED，`docker info` 连不上 npipe，如果索引层强依赖 Docker，整条开发链会被卡死。**被否决的方案**是"两套实现分两个类"——会让 S3/S4/S6 到处写 `if is_lite: ... else: ...`。同时我实测出 Lite 的性能真相：2000 条上 BRUTE_FORCE 98.1ms 反而比 HNSW 109.5ms 快，N=20000 时 HNSW 也要 1206ms/query，ef 从 16 调到 128 延迟几乎不动——所以我把"性能验收"明确划到服务器版，Lite 只承担功能与 CI。

**5. 我做了什么**：写了 60 条分三类的标注检索题（exact_term / semantic / multi_hop 各 20），实现 Recall@10 / MRR / nDCG@10（含 `near_miss` 分级相关 2/1/0），并用脚本生成消融表。
**为什么这么做**：**被否决的方案**是只报一个总分。总分 0.88 掩盖不了 `exact_term` 子集只有 0.71 的事实；而且 RRF 与 weighted-sum 的差距在总分上往往只有 1–2 个百分点，只有分组看才能说清"谁在哪类 query 上赢"。另外 80/20 划分与"test 只在阶段末跑一次"是反作弊要求，避免在测试集上反复试参。

**6. 我做了什么**：把 `RetrievedChunk` 设计成 `@dataclass(frozen=True)`，字段覆盖 S3 重排与 S4 置信度所需的全部元数据（`evidence_level / rec_strength / section_path / chunk_type / page_start / page_end`），并用 `dataclasses.replace()` 的加字段模式让下游"只加不覆盖"。
**为什么这么做**：**被否决的方案**是用 pydantic model —— S3 的 reranker 走 `replace()`，pydantic 得改 `model_copy`，而且每次校验比 dataclass 慢一个量级，50 条候选 × 每阶段一次不值得。`frozen=True` 还有个实际好处：融合阶段同一个 chunk 会从两路各产生一个实例，可变对象容易被就地改坏。
